# 异常兜底与人工接管

默认任何步骤都可能失败，但不同失败需要不同处理。无差别重试通常会把小故障变成重复副作用或费用失控。

## 失败分类与默认动作

| 类型 | 例子 | 是否重试 | 默认动作 |
|---|---|---|---|
| 临时故障 | 网络抖动、限流、短时服务不可用 | 有条件 | 有上限退避重试，尊重服务端等待提示 |
| 业务拒绝 | 余额不足、订单状态不允许 | 否 | 返回明确业务原因，进入业务处理 |
| 输入错误 | 缺字段、类型或范围错误 | 修正后 | 校验并补充，不重复发送相同错误输入 |
| 权限失败 | 凭证失效、权限不足 | 否 | 停止，确认身份和最小授权 |
| 未知状态 | 超时但不知道是否已扣款或发信 | 禁止直接重试 | 先用原请求标识查询真实状态 |
| 模型契约错误 | JSON 缺字段、越界决定、无证据结论 | 有限修正 | 模式校验、一次受控修正或降级人工 |
| 部分成功 | 库存已锁但付款失败 | 视步骤而定 | 执行预先设计的补偿或人工处理 |
| 流程中断 | 进程重启、等待审批期间退出 | 从检查点恢复 | 恢复状态，不重复已完成副作用 |

## 重试政策

每个可重试动作明确：最大次数、等待策略、总时限、可重试错误、不可重试错误和耗尽后的处理。

重试前检查：

- 操作是否无副作用，或是否有可靠幂等保护。
- 原请求是否可能已经成功。
- 输入和权限是否发生变化。
- 服务是否明确要求等待。
- 重试是否仍在费用和时间预算内。

不要让模型自行决定无限继续。

## 幂等与未知状态

幂等意味着同一业务请求即使重复到达，也只产生一次业务效果。

对于付款、退款、发消息、创建记录、修改权限等操作：

- 在第一次调用前生成稳定的业务请求 ID 或幂等键。
- 重试沿用同一个标识，不能每次生成新请求。
- 服务端或本地状态存储应能识别重复请求。
- 超时后先按标识查询原请求状态。
- 无法确认状态时进入人工队列，不猜测成功或失败。

## 补偿

部分成功时不一定能真正回滚。设计时区分：

- **可逆**：可以恢复原状态且没有外部观察者。
- **可补偿**：不能抹去事实，但可执行相反或修复动作，例如退款或释放库存。
- **不可逆**：消息已被阅读、数据已公开、法律承诺已发出，只能止损和人工处理。

需要补偿的步骤，在执行风险动作前登记补偿方式、所需信息和负责人。补偿自身也必须可追踪、可重试或可升级。

## 检查点与恢复

在有业务意义的状态变化后保存：

- workflow 和业务实例标识。
- 已完成步骤及其结果证据。
- 当前权威业务状态。
- 使用过的请求 ID、幂等键和外部对象 ID。
- 待执行任务、待审批请求和截止时间。
- 可以安全重试、必须查询状态和需要人工确认的项目。

恢复时读取检查点和权威业务系统，处理二者差异，再决定下一步。恢复不能仅依赖聊天历史，也不能重新播放已经产生副作用的动作。

## 人工介入

明确触发条件：高风险审批、规则外例外、证据冲突、未知副作用状态、连续失败、成本超限或无法满足承诺。

交给真人时提供：目标、当前状态、已完成动作、证据链接、待决定问题、可选动作和各自影响。人工审批要能暂停并在稍后恢复；超时、拒绝和撤回都应有明确状态。

## 熔断与降级

当同类失败持续发生、外部服务异常或成本失控时：

- 停止自动调用，防止扩大影响。
- 转为只读、排队、人工或简化功能。
- 告知用户哪些功能不可用，不伪装正常结果。
- 记录恢复条件，验证依赖恢复后再逐步开放。

## 错误报告

错误交付必须回答：哪里失败、之前什么已成功、系统现在处于什么状态、是否有外部影响、哪些动作能安全重试、谁需要做什么。修复后添加回归测试、监控或约束，不能只说“现在好了”。

## 协作恢复补充

多 Agent 检查点还需保存任务与尝试标识、输入版本、验收状态、依赖关系、失败路线索引和已用/预留预算。重启不能清空累计消耗或重新接纳旧结果。

当一个已接受结论被证伪，沿依赖关系标记失效，停止受影响下游，只保留仍有效的已验收产物。恢复节点由有效证据决定，不能简单退回上一条聊天；已发生的外部动作仍按权威状态对账与补偿。详见 [协作控制](multi-agent-coordination.md)。

## 把恢复路径落实到产品

按 [产品任务模型](product-task-model.md) 将失败分类映射到可用动作：明确哪些工作已保留、哪里等待、下一步由谁处理。查询、重试、补偿和人工接管都要有后台前置条件；未知状态时不直接开放再次执行或盲目补偿。

页面关闭与工作流中断分开处理：只有持久化后台、任务存储与恢复机制已经成立时，才承诺离线继续。多执行者自动接管还需验证租约或等效所有权隔离，拒绝旧执行者回写；心跳超时不能被当作业务执行失败。

用户改目标、否决结果或撤销权限时，保存新版本，重算受影响依赖和可执行动作；用户接管期间禁止自动执行者继续争写，返还自动化时重新校验状态和授权。
