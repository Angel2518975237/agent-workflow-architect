# 任务产品模型与用户控制

设计 Agent 产品的任务详情、进度、确认、恢复或接管时读取。它描述用户体验与后台状态的共同契约，不要求简单聊天产品实现一整套调度平台。

## 任务是可追踪的业务对象

长流程至少保留：任务/父任务 ID、业务目标、范围、优先级、任务与计划版本、输入快照引用、子任务与依赖、责任方、当前阶段、状态、产物、验收契约、失败与重试记录。证据和权限用引用关联，避免复制出不一致版本。数据快照按权限与保留期最小化保存。

负责人可能是一个 Agent、确定性程序或真人；不按 Planner 等名字强行拆分。允许改计划的角色还要有改动范围、失效分析和审计责任。供应商或 Agent 替换保留契约、任务标识与验收要求；新执行者只获得所需数据和权限。

界面分层呈现：

- **概览**：目标、业务阶段、已验证成果、阻塞原因、下一步与用户待办；时间和成本只有依据时才估计，不伪造进度百分比。
- **子任务**：负责方、输入版本、依赖、状态、产物与验收结果；原始 Agent 标识可在详情中展开。
- **依据与活动**：结论到证据、重要状态变化、审批与工具操作记录。普通用户看业务说明，运营人员按权限查看必要追踪信息。

## 状态分层，避免一个“失败”承载所有含义

以下是可裁剪的概念模型，实施时定义枚举、合法转换、版本校验和事件写入者：

| 维度 | 示例值 | 决定什么 |
|---|---|---|
| 任务生命周期 | 待执行、执行中、等待、暂停中、已暂停、取消中、已取消、失败、已完成 | 是否仍调度任务，用户可以采取哪些动作 |
| 等待原因 | 等输入、等授权、等依赖、等验收、等外部状态核实 | 谁需要处理，超时后去哪里 |
| 单次外部动作 | 未执行、已提交/处理中、成功、失败、未知 | 能否查询、重试或补偿；一个任务可有多条动作记录 |
| 产物验收 | 待验收、通过、退回、失效 | 哪些产物可供下游采用 |
| 证据状态 | 按证据记录定义 | 什么能作为事实、什么仍需验证 |

阶段表示“现在在检索还是测试”，不等于状态。等待授权与外部状态未知可以同时出现，不能互相覆盖。整体完成要求当前版本的必要产物通过验收、关键外部动作得到业务确认；不能以所有 Agent 停止或请求返回成功代替。

完成部分子任务时保留其产物，概览显示“已完成部分 + 剩余阻塞”，而非整项成功。父任务根据必要依赖与验收聚合；可选任务失败是否影响完成应在范围中预先约定。取消只表示后续调度结束；仍有外部未知动作时持续显示待核实标记和处理责任，不能显示“全部撤销”。

## 用户动作要有前置条件与后果

| 动作 | 系统行为与界面承诺 |
|---|---|
| 暂停 / 继续 | 停止新调度；核对在途工具能否中断，达到安全点后才显示已暂停。继续前复核权限、输入版本与预算 |
| 修改目标 / 补资料 / 否决结论 | 生成修订版本，分析依赖，暂停受影响下游；保留仍有效成果并重新验收受影响部分。用户否决阻止采用，不自动证明结论客观为假 |
| 调整优先级 / 改路线 | 说明对等待、成本和执行顺序的影响，不绕过依赖与验收。新范围或新增副作用需核对原授权是否覆盖 |
| 只重试失败步骤 | 先分类错误并核对副作用状态、幂等与重试预算；只重跑失败步骤及失效依赖，不重放已成功动作 |
| 查询外部状态 | 对未知动作提供原请求关联查询；证据不足继续标未知，不能把超时转成已失败 |
| 更换 Agent / 重新分配 | 撤销原执行租约或写入权，交接检查点与权限，拒绝原执行者迟到写入；不重置任务成本或重试次数 |
| 修改 / 撤销权限 | 更新授权版本并阻止后续不再允许的调用；已经提交的操作另行核实，不宣称撤权自动撤销既有影响 |
| 取消 / 人工接管 | 停止自动新动作并移交状态、证据、待办和在途请求；真人与自动执行者不能同时写同一业务状态 |
| 回滚 / 补偿 | 确认已发生影响、可逆性、当前状态和对应授权后才提供；补偿本身有副作用，需要单独追踪 |

无法安全执行的按钮应隐藏或禁用并解释原因；后端仍须强制校验，不能只靠界面禁用。未知状态优先查询或人工核实；重试和补偿只有满足安全条件时才开放。详见 [异常恢复](resilience.md)。

## 用户改变方向时保持一致

用户发出修正后，记录当前目标与输入的新版本；把受影响产物标为待复核或失效，通知或停止相关执行者。结果提交要校验任务、输入版本与写入归属，不能让旧输出覆盖新指令。进行中的不可逆动作不能保证立即停止，应明确已提交的内容和后续处理。

请求用户确认绑定具体动作与材料版本。确认期间目标、参数或权限发生实质变化时，旧确认不得用于新动作；仍在原授权范围内且条件未变的执行不重复索取批准。验收范围改变需要留下理由并重评，不能为了通过而偷偷删掉失败项。

## 后台持续运行与接管

长时间运行时明确执行是在客户端还是持久化后台。关闭页面后的继续执行、结果通知与恢复只能在已有实现和授权下承诺；没有后台能力时如实说明，并提供可恢复检查点。

存在多个执行节点或自动故障接管时，设计租约、心跳和写入代次：心跳丢失只证明失联，不证明工具失败；新执行者接管后，存储或工具边界应拒绝旧代次写入。外部系统不支持这种隔离时，需额外使用幂等、串行锁或对账，不能仅凭本地租约保证无重复副作用。单进程简单任务不强制引入分布式机制。

## 用一条场景检查产品闭环

已获授权的发布请求超时：概览显示“发布结果待核实”，并保留构建与测试产物；不能直接展示“重新发布”。系统按原请求号查询：若确认部署成功，继续业务健康验证；若确认未执行且权限与版本仍有效，允许安全重试；持续未知则暂停相关动作并提供人工接管。最终健康验证通过才按原验收契约完成。

这条场景同时检验了状态、按钮、权限、证据与恢复是否指向同一真实结果。
