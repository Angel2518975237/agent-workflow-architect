# 多 Agent 协作

多 Agent 的默认代价是更多上下文传递、冲突、延迟、费用和调试难度。只有独立专业能力、真实并行、权限隔离或独立复核带来明确收益时才使用。

## 默认结构：负责人调用专家

```text
用户 ↔ 总负责人
        ├─ 业务或领域专家
        ├─ 实现专家
        ├─ 测试专家
        └─ 独立审查者
```

总负责人保留：

- 用户关系和目标解释权。
- 任务拆解、依赖与授权边界。
- 共享状态和最终产物的责任。
- 冲突裁决和最终结论。

专家提交有边界的结果，不直接争夺最终答案。

## 什么时候使用交接

当后续 Agent 应完整接管对话、拥有独立专业流程，而且用户不需要原负责人持续聚合时，可以交接。否则优先由负责人把专家当作受控能力调用。

交接前过滤上下文：只传目标、已确认事实、相关证据、约束和未决问题。不要默认传完整聊天、所有工具输出和其他 Agent 的草稿；这会放大偏见、泄露无关数据并污染判断。

## 委派契约

每项委派必须包含：

```yaml
goal: 一个可验证结果
context: 最小必要事实与证据
inputs: 可读取的文件、数据或前序产物
output_contract: 结构和必填内容
write_scope: 唯一允许修改的目标
acceptance: 验证命令或判断标准
stop_conditions: 必须停止并上报的情况
```

不要只说“研究一下”“帮我看看”或“做得全面一点”。

## 五条协作硬规则

1. **一个产物，一个写入负责人。** 其他 Agent 只能提交建议、补丁或审查发现。
2. **先证明独立，再并行。** 依赖前序结果或共享写入目标的任务保持串行。
3. **共享事实，不共享噪声。** 用结构化交付和证据引用，不让 Agent 自由闲聊。
4. **分歧带证据。** 明确裁决者；涉及业务价值取舍时交给用户。
5. **讨论有停止条件。** 默认一轮实现、一轮独立审查、一轮修正；继续必须有新证据或未通过的验收项。

## 聚合与验收

总负责人不能拼接答案后直接交付。必须检查：

- 专家是否回答了任务，而不是扩展了范围。
- 输出契约是否满足，引用和运行证据是否存在。
- Agent 之间的假设、术语、接口和状态是否一致。
- 是否存在重复工作、互相覆盖或无人负责的缺口。
- 关键风险是否经过独立视角检查。

## 失败处理

- 专家超时：判断任务能否安全降级、缩小或重新委派，不无限等待。
- 输出不合格：指出具体缺口，最多进行有边界的修正轮次。
- Agent 冲突：比较证据、业务目标、风险和成本，不进行无上限投票。
- 部分完成：保留已验证产物，标记未完成依赖，避免全量重做。
- 负责人失败：不得让某个专家默默接管权限；需要显式恢复或人工介入。

## 观测指标

记录任务成功率、返工次数、关键路径耗时、模型与工具成本、上下文大小、交接次数和冲突原因。新增 Agent 后如果质量没有可测提升，或协调成本超过收益，就回退到更简单架构。
