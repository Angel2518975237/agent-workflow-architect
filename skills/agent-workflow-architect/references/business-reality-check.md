# 业务现实检查

目标不是证明想法“理论上能做”，而是判断它依赖的业务、数据、工具和运营条件在现实中是否成立。

## 七个检查视角

### 1. 业务闭环

- 谁或什么事件触发流程？重复触发怎么办？
- 输入来自谁，谁有权确认它是真的？
- 中间决策依据哪些明确规则？
- 业务上怎样才算完成，而不只是 Agent 返回了一段文字？
- 失败、取消、超时和部分成功后，业务状态是什么？
- 最终由谁承担结果责任？

### 2. Agent 是否合适

- 这一步需要理解模糊信息、权衡或生成内容吗？如果不需要，优先确定性程序。
- 错误答案是否容易被发现和纠正？越难发现，越不适合让模型独立决定。
- 同样输入是否必须永远得到同样结果？如果必须，核心判断不能只靠模型。
- 是否因为“想做 Agent”才把规则引擎、搜索、计算或表单包装成 Agent？

### 3. 数据现实

- 数据源真实存在吗，还是停留在“以后接一下”的设想？
- 数据是否完整、及时、可关联、可追溯？
- 空值、脏数据、重复记录和历史口径变化如何处理？
- 是否有权限使用、保存和传给模型？保存多久，谁能删除？
- 测试数据是否代表真实分布，而不只是几个漂亮样例？

### 4. 工具现实

- 接口和所需操作是否真的提供，而不只是产品页面看起来支持？
- 凭证、权限范围、限流、费用、超时和地区限制是否确认？
- 工具返回“成功”代表请求被接收，还是业务动作已经完成？
- 版本升级、字段变化和服务中断由谁维护？

### 5. 执行现实

- 同一请求重复到达会不会产生两次副作用？
- 两个任务同时修改一条数据时谁赢？
- 流程中途重启后从哪里恢复？
- 前三步成功、第四步失败时怎样处理已经发生的影响？
- 日志能否回答“谁、何时、基于什么输入、调用了什么、结果如何”？

### 6. 模型现实

- 模型可能误解、编造、遗漏字段和输出格式漂移。
- Prompt 是建议，不是事务、权限或数据约束。
- “置信度 90%”通常不是经过校准的真实错误概率。
- 长上下文可能稀释关键规则，旧记忆可能污染新决策。
- 升级模型、Prompt 或工具描述可能改变行为，必须用代表性样例回归。

### 7. 运营现实

- 谁看失败队列、告警和成本？多久响应？
- 哪些规则会变化，谁能安全更新？
- 失败率、单次成本或处理时长达到什么阈值应降级或停用？
- 人工接管是否真的有人、有界面、有上下文，而不是文档里写了“转人工”？
- 上线是有限试运行还是全量自动化？如何快速关闭？

## 发现格式

每个重要发现都按以下链路表达：

```text
用户当前方案
→ 隐含假设
→ 现实失败场景
→ 影响对象和严重度
→ 证据状态
→ 最小安全修正
```

示例：

> 当前方案在工具超时后直接重试退款，隐含假设是“超时等于没执行”。现实中第一次退款可能已经成功，只是响应丢失；第二次调用会造成重复退款，属于阻断问题。接口的查询能力尚未验证。最小修正是使用唯一退款请求号，并在重试前查询原请求状态。

## 验证顺序

1. 先验证会推翻整个方案的关键假设。
2. 优先使用只读检查、官方文档、真实接口描述或小范围实验。
3. 用最低成本确认“能不能”，再优化“好不好”。
4. 无法马上验证时，标记负责人、方法和截止条件；不要静默当成事实。

## 原型与生产的区别

原型可以使用假数据、人工触发和有限错误处理，但必须明确标注。涉及资金、敏感数据、生产写入或用户承诺时，即使名为原型也不能跳过权限与副作用保护。

评估开发难度时同时说明：核心技术难度、系统集成难度、数据准备、测试成本、运营负担和长期维护。不要只估算写代码的时间。
