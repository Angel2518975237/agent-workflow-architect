# 从业务拆成 Agent 任务

拆解目标不是产生更多任务，而是形成能够独立理解、验证和交付的业务切片。

## 从业务闭环开始

先画出最短闭环：

```text
触发 → 获取事实 → 作出决定 → 执行动作 → 验证业务结果 → 处理例外
```

逐项标记：

- **判断型**：信息模糊、需要语义理解或权衡，可能适合 Agent。
- **确定型**：校验、计算、权限、状态变更，优先代码或规则。
- **工具型**：查询或改变外部系统，需要明确契约。
- **人工型**：价值取舍、高风险审批、例外处理或责任确认。

不要先按技术层拆成“数据库、API、Prompt、前端”。这种清单便于分工，却不能证明任何业务价值已经成立。

## 垂直切片

每个切片应从真实输入走到可验证结果。例如：

```text
切片 1：读取一条客户反馈并归入已有类别，由人工确认准确率
切片 2：对无法归类的反馈提出候选类别，不自动创建
切片 3：聚合同类反馈并生成带来源链接的摘要
```

每个切片写明：

- 业务结果与使用者，以及用户如何看进度、处理阻塞和确认结果（如需要）。
- 输入、输出和状态变化。
- Agent、代码、工具和真人各自责任。
- 可观察的完成标准。
- 明确不包含什么，谁可修改范围，以及改动会使哪些输入、产物和验收条件失效。
- 失败时是否安全、如何恢复。

## 任务契约

实施任务至少包含：

```yaml
goal: 要改变的可观察结果
inputs: 已确认的事实、文件和接口
owner: 唯一负责人
dependencies: 必须先完成的任务
output: 可检查的交付物
acceptance: 通过条件与验证方法
boundaries: 不得擅自改变的范围
failure_escalation: 遇到何种情况停止并上报
```

## 依赖和并行

先画依赖，再决定并行：

- 不读取彼此输出、不同写入目标的任务可以并行。
- 共享同一状态或文件的任务应明确单一写入者。
- 通过接口契约和模拟数据解除不必要依赖。
- 钻石依赖要明确聚合者和冲突解决规则。
- “多个 Agent 同时想办法”不是有效并行，除非需要独立观点且有选优标准。

## 不确定性 Spike

关键假设未验证且不同答案会改变架构时，先做限时验证任务，而不是给整个项目虚假估期。

Spike 必须有：

- 要回答的一个具体问题。
- 时间上限。
- 最小实验或证据来源。
- 输出：结论、证据、选项、代价和修订后的计划。
- 到时仍未知时的决策方式。

## 完成标准

使用“给定—当—那么”或同等明确的业务例子。避免“优化体验”“完善异常”“接入模型”等不可验证表述。

开始前检查：

- 范围能否被一个负责人完整理解？
- 是否在较短周期内产生可验证价值？
- 依赖、状态所有者和外部副作用是否清楚？
- 是否有正常路径和至少一个关键失败路径？
- 测试能否证明业务结果，而不只是函数返回？

任一答案为否，就继续拆解或先做 Spike。

## 拆分收益检查

把业务拆成步骤，不等于把每一步分给不同 Agent。并行委派前核对：独立输入与目标、可单独验收的结果、能够覆盖协调成本的收益。任一条件缺乏证据时，优先保留完整上下文或做限时对照。

需要独立复核或权限隔离时可以有顺序依赖，但必须说明其质量或风险收益。更多协作控制见 [多 Agent 协作](multi-agent-coordination.md)。
