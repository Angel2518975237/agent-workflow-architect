# Agent 架构判断

架构目标是用最少的不确定性解决业务问题，而不是最大化 Agent 数量。

## 用业务问题逐步选型

先从已有资料判断，只问仍会改变方案的缺口，每次优先一个问题。让用户描述真实任务与限制，由 Skill 作架构判断；不要要求用户自行确认“一个 Agent 能不能搞定”。

### 1. 执行路径能否提前确定？

可问：“这件事每次都按固定步骤和已知分支处理，还是需要拿到中间结果后，才决定接下来查什么、做什么？能举一次实际例子吗？”

步骤、条件分支和异常处理可预定义时，优先 **Workflow**。固定流程也可以调用模型做分类、提取或生成，不因此成为自主 Agent；能由规则、计算或程序可靠完成的部分优先用代码。路径本来可确定但需求尚未梳理清楚时，先澄清，不能把“暂时不知道步骤”当作需要 Agent。

如果需要根据新信息自主决定下一步，定位真正需要探索的环节，进入下一问；不是把整个业务交给自由规划。

### 2. 一个 Agent 加工具是否足够？

可问：“哪些情况现在最难处理？主要是资料或工具拿不到、规则没讲清、结果不可靠，还是耗时、费用或权限隔离达不到要求？”

由 Skill 结合目标、上下文、工具与完成标准判断，必要时做小样例验证。一个 Agent 可在限额内完成时，优先 **Single Agent**。没有基线时标记待验证，不直接认定不够用。先排除数据、工具、需求和权限缺口；增加 Agent 不能解决这些根因。

### 3. 子任务是否相对独立且能单独验收？

可问：“哪些部分可以拿着各自的材料先做，不必反复等待其他部分？每部分交付什么，怎样判断它做对了？”

- **独立且可验收**：再比较质量、耗时与总成本；收益覆盖交接、等待、复核和同步成本时考虑 **Multi-Agent**，否则保留更简单方案。并行读取或程序计算也不一定需要多个 Agent。
- **紧密依赖**：保持上下文与状态链。若能提取固定骨架，把探索判断留给一个 Agent，由 Workflow 保证顺序、权限和恢复，采用 **Agent + Workflow**。若没有可稳定定义的骨架，先缩小范围或验证关键难点，不强行推荐混合架构。
- **有独立复核或权限隔离要求**：可采用受控的顺序多 Agent，不要求所有子任务都能并行，但需说明必要性和额外成本。

### 决策导航

```text
用户任务
  ↓
路径与条件分支能否预定义？
  ├─ 能 → Workflow（按需包含模型调用）
  ├─ 尚不清楚 → 澄清实际案例或做限时验证
  └─ 需要随结果自主决策
       ↓
     一个 Agent + 工具能否达到验收与资源要求？
       ├─ 能 → Single Agent
       ├─ 尚无证据 → 最小基线验证
       └─ 有明确不足，且已排除数据/工具/需求缺口
            ↓
          子任务是否相对独立且可单独验收？
            ├─ 是 → 比较收益与协调成本 → 值得才用 Multi-Agent
            └─ 否 → 有固定骨架：Agent + Workflow
                     无固定骨架：缩小范围或继续验证
```

这是提问导航，不是互斥分类：Workflow / Agent 描述谁决定执行路径，Single / Multi 描述执行者如何组织。多 Agent 也可以受 Workflow 调度；不要把这里的 Agent + Workflow 与下文多 Agent 拓扑中的 Hybrid 混为一谈。

选型后给出：推荐架构、对应的用户事实、排除其他方案的原因、待验证项与最小下一步。若需要持续档案，写入 Blueprint；不要只回复一个架构名称。真人决定、权限与不可逆动作的边界在所有分支都需要按实际风险检查。

## 单 Agent 与多 Agent

优先单 Agent，当：

- 任务共享一套上下文和成功标准。
- 工具调用链紧密相连，拆分会反复复制上下文或同步中间状态。
- 不需要权限隔离或独立复核。
- 延迟、费用或调试难度敏感。

考虑多 Agent，当：

- 专业任务能清晰分开，输入输出契约稳定。
- 独立任务可以真正并行。
- 高风险结果需要与实现者分离的审查者。
- 不同 Agent 必须拥有不同权限或数据视图。

不要用多 Agent 修复一个定义不清的目标。模糊任务分给更多 Agent 只会产生更多互相矛盾的答案。

## 责任边界

为每个 Agent 明确：

- 单一职责和明确目标。
- 所需最小上下文。
- 可以读取和写入的资源。
- 可调用工具及其风险等级。
- 结构化输入、输出、禁止事项和拒绝条件。
- 能否调整计划，调整的范围与受影响产物的失效规则。
- 成功标准、超时和升级路径。

Agent 不应自己扩大目标、增加权限或把未确认推断写成事实。

## 状态所有权

每一类业务状态只能有一个权威来源和一个明确写入责任方。区分：

- **会话上下文**：只为当前交互服务，不等于长期事实。
- **工作流状态**：当前步骤、已完成动作、待审批和恢复信息。
- **业务系统状态**：订单、客户、资金等权威记录。
- **长期记忆**：经过筛选、可修正、有来源和生命周期的知识。

不要让自由文本聊天记录成为生产状态。跨 Agent 传递结构化摘要和证据引用，而不是默认转发全部历史。

## 关键约束落点

以下约束不能只写在 Prompt：

- 权限和资源范围。
- 必填字段、数值范围和格式。
- 必须调用的验证工具。
- 幂等、并发和唯一性。
- 审批门槛与不可逆操作。
- 最大轮次、费用和重试次数。

Prompt 负责意图和判断指导；代码、模式校验、数据库约束和工具护栏负责强制执行。

## 模型不确定性

模型给出的“置信度”只有经过代表性数据校准后才有业务意义。更可靠的做法是：

- 要求证据来源和可验证字段。
- 对关键输出使用结构化模式校验。
- 将低证据、矛盾或超范围结果路由到人工。
- 用真实失败样例测试，而不是依赖模型自评。

## 推荐产物

架构设计至少说明：业务目标、Agent/代码/真人边界、状态所有权、数据流、工具权限、主要失败路径、人工介入点和最小验证方案。

## 按信息流选择拓扑

以下是选型起点，最终用代表性任务验证，不用角色名称代替控制关系。

| 拓扑 | 适合的任务条件 | 主要代价与拦截位置 |
|---|---|---|
| Single-Agent：一个 Agent 保持完整上下文 | 严格串行、状态紧耦合，或基线已满足目标 | 单点判断可能出错；由工具校验、测试或必要的独立复核拦截 |
| Independent：各自执行，末端聚合 | 输入独立、子结果可单独验收 | 中途缺少互查；每个结果必须先验收再参与聚合 |
| Centralized：负责人调度与验收 | 需要统一状态、跨子任务整合 | 负责人可能拥塞或带入共同偏见；保留原始证据和独立验收通道 |
| Decentralized：直接交换证据和质疑 | 确有点对点协商收益 | 通信和回放复杂；限定消息轮次、状态写入者和最终裁决规则 |
| Hybrid：集中控制加局部直接协作 | 少数局部问题需要相互质疑 | 明确局部讨论边界，统一预算和最终验收，避免双重指挥 |

需要多 Agent 且无相反证据时，可从集中式小团队开始。不要强迫去中心化方案设置全局唯一调度者，但每项产物、争议和权限都必须有明确归属。

分开描述三个层次：拓扑决定信息和控制如何流动；协作模式决定候选、质疑、验收和修订如何推进；角色只决定当前谁负责。一个 Reviewer 角色并不自动构成有效的审查控制路径。

记录选定方案、排除其他方案的原因、待验证假设和回退条件。实测比较见 [协作评估](coordination-evaluation.md)。
