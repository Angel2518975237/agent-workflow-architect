# 阶段识别与路由

先判断用户要达成什么，再判断缺少什么。不要让用户学习阶段名称或手工选择模式。

## 八种主模式

| 主模式 | 可观察信号 | 优先检查 | 主要产物 | 应停止实施的情况 |
|---|---|---|---|---|
| 业务澄清 | “我想做一个……”但价值、对象或完成标准模糊 | 用户、触发、结果、指标 | 精简业务说明 | 关键业务决定会被代码暗中代替 |
| 现实可行性 | 询问“能不能做”“难不难”或方案依赖未知能力 | 数据、接口、权限、费用、运营 | 可行性结论与验证清单 | 核心依赖尚未证实且会改变方案 |
| 任务拆解 | 需求过大、无法估算、依赖混乱 | 业务闭环、垂直切片、验收 | 任务图与完成条件 | 任务只有技术动作，没有可验证价值 |
| 架构设计 | 单/多 Agent、角色、记忆、状态等问题 | Agent/代码/真人边界 | 角色、状态与数据流 | 高风险决策仅依赖 Prompt |
| 工具编排 | 调什么工具、先后顺序、效率与权限 | 前置条件、副作用、校验 | 调用 DAG 与工具契约 | 工具、目标或授权尚未确认 |
| 异常设计 | 重试、失败、中断、回滚或审批 | 幂等、未知状态、补偿 | 失败矩阵与接管策略 | 副作用重复风险没有控制 |
| 工程实现 | “帮我做/改/接入/测试” | 当前代码、前置设计、项目命令 | 可运行实现与证据 | 缺失决策会造成不可逆或大规模返工 |
| 上线审查 | “能不能上线”“帮我审查” | 代码、测试、追踪、运营 | 分级发现与发布结论 | 存在阻断问题 |

## 路由算法

1. 从用户目标、已有 Blueprint、项目文件和验证证据判断主模式。
2. 添加必要的风险标签：资金、敏感数据、外部写入、权限、不可逆、长流程、共享状态、生产。
3. 只为这些标签加载交叉参考。例如退款架构需要工具编排和异常恢复；普通文案 Agent 不自动加载全部审查规范。
4. 判断是否越级：当前动作是否依赖一个尚未决定或尚未验证的前提。
5. 越级且风险高时暂停；越级但风险低、可逆时可以做标注清楚的最小原型。

## 证据状态

- **已确认事实**：来自用户明确决定、代码、配置、真实工具返回或测试结果。
- **合理推断**：有上下文支持，但尚未由权威来源或运行结果确认。
- **尚未决定**：需要业务负责人做取舍。
- **尚未验证**：答案客观存在，可以通过检查或实验确认。
- **已发现风险**：有具体失败机制和影响，不是抽象担忧。

推断不能直接变成业务规则。先标记，再决定是询问用户还是做低成本验证。

## 简单任务逃生口

满足以下条件时直接处理：范围明确、低风险、可逆、不产生外部副作用、不改变核心架构，并且有清楚的完成标准。不要创建完整 Blueprint，不要召集多 Agent，不要进行生产级审查。

## 追问原则

只有缺失信息会实质改变方案或带来风险时才追问。一次只问最关键的问题；能从项目和工具中安全查明的事实，先查明再问。
